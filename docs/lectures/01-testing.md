# Лекция 1. Тестирование в delivery-backend

> Цель: понять, какие тесты есть в проекте, зачем каждый уровень, как их запускать и как читать результат.
> Лекция идёт снизу вверх по «пирамиде»: от быстрых unit-тестов до нагрузки и профилирования.
> Во второй лекции ([02-observability-grafana.md](02-observability-grafana.md)) — логи, метрики, трейсы и Grafana.

---

## 0. Зачем вообще столько видов тестов

Каждый вид теста отвечает на свой вопрос. Ни один не заменяет другие.

| Вопрос | Вид теста | Цена (скорость, хрупкость) |
|---|---|---|
| Правильна ли логика функции? | **unit** | миллисекунды, без Docker |
| Не падает ли код на странном входе? | **fuzz** | секунды-минуты, без Docker |
| Работает ли код с настоящим Postgres/Kafka? | **integration** | секунды, нужен Docker |
| Работает ли система целиком, как её видит клиент? | **e2e** | десятки секунд, весь стек |
| Сколько выдерживает и где узкое место? | **load** (k6, ghz) | минуты-часы, изолированный стек |
| Не стал ли горячий код медленнее? | **benchmark** + benchstat | секунды-минуты |
| На что тратится CPU/память? | **профилирование** (pprof, Pyroscope) | по запросу |

Отсюда **пирамида тестов**: внизу много дешёвых unit-тестов, выше — меньше integration, ещё меньше e2e,
на вершине — редкие тяжёлые нагрузочные прогоны.

```
              ▲  load / soak        — редко, руками, минуты-часы
             ▲▲▲  e2e                — 7 сценариев, весь стек в compose
           ▲▲▲▲▲▲  integration        — реальные Postgres / Redpanda в testcontainers
     ▲▲▲▲▲▲▲▲▲▲▲▲▲▲ unit + fuzz        — сотни быстрых тестов без I/O
```

Правило: **ловить ошибку на самом нижнем уровне, где она вообще ловится.** Если баг можно поймать
unit-тестом — не нужно ради него поднимать весь стек.

### Карта уровней в проекте

Эпик описан в [`spec/specs/testing/map.md`](../../spec/specs/testing/map.md), спеки модулей рядом.

| Уровень | Команда | Что нужно | Где лежит |
|---|---|---|---|
| unit | `task test` | ничего | `*_test.go` без build-тега |
| fuzz | `task fuzz` (`FUZZTIME=30s`) | ничего | `func FuzzXxx` |
| integration | `task test-integration` | Docker | `*_integration_test.go`, тег `integration` |
| покрытие | `task cover` | Docker | `.testcoverage.yml` в каждом модуле |
| e2e | `task e2e` | Docker | модуль `e2e/`, тег `e2e` |
| benchmark | `task bench`, `task bench-compare` | ничего | `bench_test.go`, эталон `load/bench/baseline.txt` |
| load | `task load-up`, `task load-smoke/stress/regression/soak`, `task load-grpc` | Docker | `load/` |
| pprof | `task pprof SERVICE=order` | запущенный сервис | `platform/debugserver` |

CI нет: всё запускается локально, но задачи Taskfile написаны так, чтобы CI потом просто их вызывал.

## 1. Общие конвенции (модуль `test-foundation`)

Прежде чем смотреть на тесты, полезно знать «правила игры», общие для всех уровней.

### 1.1. Флаги `go test`, которые используются везде

```bash
go test -race -shuffle=on -count=1 ./...
```

- `-race` — детектор гонок данных. Если две горутины пишут в одну переменную без синхронизации, тест упадёт
  с отчётом `WARNING: DATA RACE`. Медленнее, но ловит самый неприятный класс багов.
- `-shuffle=on` — случайный порядок тестов. Если тест A незаметно готовит состояние для теста B,
  перемешивание это вскроет. При падении в выводе есть `-shuffle=<seed>` — повторите с ним.
- `-count=1` — отключает кеш результатов `go test`. Иначе Go может показать `(cached)` и ничего не запустить.

### 1.2. Build-теги разделяют уровни

Первая строка файла решает, к какому уровню он относится:

```go
//go:build integration   // запустится только с -tags=integration
//go:build e2e           // запустится только с -tags=e2e
```

Поэтому `task test` не требует Docker: integration- и e2e-файлы просто не компилируются.

### 1.3. Библиотеки

- **testify**: `require` — останавливает тест при первой ошибке (по умолчанию);
  `assert` — продолжает, удобно для нескольких независимых проверок подряд.
  `testify/suite` **не используется**: плохо сочетается с `t.Parallel`.
- **mockery v3** генерирует типизированные моки (`task mocks`, конфиг `.mockery.yml`).
  У них метод `EXPECT()` — компилятор проверит имя метода и типы аргументов.
- **goleak** — проверяет, что после тестов не осталось «забытых» горутин.
- **testcontainers-go** — поднимает Postgres/Redpanda в Docker прямо из теста.

### 1.4. Стиль

- Табличные тесты (table-driven): срез кейсов + цикл `t.Run(tt.name, ...)`.
- `t.Parallel()` в тесте и в каждом подтесте.
- Имена кейсов на английском (`"propagates user service error"`), комментарии на русском.

## 2. Unit-тесты

### 2.1. Что это

Unit-тест проверяет **один кусок логики в изоляции**: без сети, БД, файлов. Всё внешнее заменено
подделками. Поэтому он быстрый (миллисекунды) и детерминированный.

В проекте unit-тестами покрыты:

- `domain` — сущности и правила (`order/internal/domain/order_test.go`);
- `service` — use case'ы с моками репозиториев и клиентов;
- транспорт — HTTP-хендлеры через `httptest`, gRPC через `bufconn` (соединение в памяти, `platform/testkit/grpctest`);
- mapper/dto, конфиги, все пакеты `platform`.

### 2.2. Разбор примера: `services/order/internal/service/order_test.go`

`OrderService.CreateOrder` зависит от пяти вещей: транзакции, репозиториев заказов и outbox,
построителя событий, клиентов `user` и `product`. В тесте:

**Ручной фейк для простой зависимости.** Транзакцию мокать бессмысленно — достаточно фейка:

```go
type fakeTx struct {
	isInTx bool
	err    error
}

func (f *fakeTx) WithinTx(ctx context.Context, fn func(ctx context.Context) error) error {
	if f.err != nil {
		return f.err // имитируем «БД недоступна»
	}
	f.isInTx = true
	defer func() { f.isInTx = false }()
	return fn(ctx)
}
```

Флаг `isInTx` позволяет проверить, что репозитории вызываются **внутри** транзакции.

**Моки mockery для остального.** Ожидания задаются через `EXPECT()`:

```go
d.users.EXPECT().GetUser(mock.Anything, "user-1").Return(domain.User{ID: "user-1"}, nil)
```

Читается так: «ожидаю вызов `GetUser` с любым ctx и id `user-1`, вернуть такого пользователя».
Моки **строгие**: если вызван метод без `EXPECT()` — тест падает; если ожидание не выполнено — тоже
падает (проверка регистрируется через `t.Cleanup` в `NewMockXxx(t)`).

**Таблица кейсов.** Каждый кейс — свой сценарий отказа:

```go
tests := []struct {
	name    string
	setup   func(d deps)
	wantErr []error
}{
	{
		name: "propagates user service error without saving order",
		setup: func(d deps) {
			d.users.EXPECT().GetUser(mock.Anything, "user-1").Return(domain.User{}, errUnavailable)
		},
		wantErr: []error{errUnavailable},
	},
	{
		// Create и Save без EXPECT: строгие моки упадут, если репозитории вызовутся при отказе транзакции.
		name: "propagates transaction error without touching repos",
		setup: func(d deps) {
			expectOrderPrepared(d)
			d.tx.err = errDB
		},
		wantErr: []error{errDB},
	},
	// ...
}
```

Обратите внимание на трюк во втором кейсе: **отсутствие** `EXPECT()` — это тоже проверка.
«Если транзакция не открылась, заказ сохранять нельзя» — и строгий мок это гарантирует.

`wantErr` — срез, потому что ошибка может быть обёрнута: проверяется `errors.Is` для каждого элемента
(например, и `domain.ErrProductNotFound`, и `apperr.NotFound()`).

### 2.3. goleak — поиск утечек горутин

В пакетах, где запускаются горутины, есть `main_test.go`:

```go
func TestMain(m *testing.M) {
	goleak.VerifyTestMain(m, /* игнор известных горутин testcontainers */)
}
```

Если после всех тестов осталась горутина (например, consumer не остановился по `ctx`) — пакет падает.
Образец: `platform/kafka/kafkaconsumer/main_test.go`.

### 2.4. Fuzz-тесты

Fuzzing — Go сам генерирует входные данные, мутируя «семена», и ищет панику или нарушение инварианта.
Нужен для **парсеров внешнего ввода**. Цели в проекте:

- `platform/http/bind/bind_test.go` — разбор HTTP-запросов;
- `services/order/internal/event/order_test.go` — построение события;
- `services/notification/internal/transport/kafka/order/handler_test.go` — разбор сообщения из Kafka.

```bash
task fuzz                 # каждая цель по 30 с
task fuzz FUZZTIME=2m
```

Если fuzz нашёл падение, вход сохраняется в `testdata/fuzz/FuzzXxx/<hash>` и с этого момента
становится обычным регрессионным кейсом при `go test`.

Реальная находка уровня unit: `notification` принимал не-UUID `event_id`/`order_id` и падал только
на INSERT в inbox. Теперь идентификаторы валидируются при разборе.

## 3. Integration-тесты

### 3.1. Что это и зачем

Моки проверяют, что код **вызывает** репозиторий правильно, но не проверяют, что SQL **работает**.
Integration-тест запускает код против **настоящего** Postgres или Redpanda (Kafka-совместимый брокер).

Ловит: опечатки в SQL, неверные миграции, нарушение транзакционности, проблемы сериализации,
поведение Kafka-consumer'а при ошибках.

```bash
task test-integration     # нужен запущенный Docker
```

### 3.2. Инфраструктура `platform/testkit`

| Пакет | Что даёт |
|---|---|
| `pgtest` | Один Postgres-контейнер на тестовый бинарь. `NewDB(t, migrationsDir)` — **отдельная чистая база** на каждый тест (клон шаблона с применёнными миграциями), поэтому тесты идут параллельно и не мешают друг другу. `CheckMigrations` — прогон up → down → up |
| `kafkatest` | Один Redpanda на бинарь. `CreateTopic` — топик с уникальным суффиксом, `Produce` — синхронная запись |
| `grpctest` | Соединения `bufconn` и фейковые gRPC-серверы |

Если Docker недоступен — тест **падает**, а не пропускается. Это осознанно: «зелёный» прогон без
реальной проверки хуже красного.

### 3.3. Что проверяется

1. **Репозитории `pg`** — CRUD против настоящей схемы
   (`services/order/internal/repository/pg/order_integration_test.go`).
2. **Миграции** — `pgtest.CheckMigrations`: применить, откатить, применить снова. После `down` в схеме
   должна остаться только `schema_migrations`. Ловит неполный `down`-скрипт.
3. **Атомарность (Unit of Work)** — если `OutboxRepo.Save` упал, откатываются и `orders`, и `order_items`
   (`tx_integration_test.go`). Это ядро паттерна Transactional Outbox: заказ и событие пишутся вместе или никак.
4. **Outbox и трассировка** — `outbox_integration_test.go` проверяет, что в строку outbox пишется
   `traceparent` активного спана. По нему потом трейс продолжится в `notification` (см. лекцию 2).
5. **Inbox и идемпотентность** — повторное сообщение не создаёт второе уведомление.
6. **Kafka-consumer** на Redpanda — коммит оффсета, откат и ретрай при ошибке, остановка по `ctx`.
7. **Контракт событий (golden-тест)** — эталон `contracts/events/order.created.json`. `order` проверяет,
   что событие в outbox совпадает с эталоном; `notification` — что эталон корректно разбирается.
   Если кто-то поменяет формат в продюсере, тест упадёт **до** того, как сломается консьюмер.
8. **Smoke-тест `app`** — сервис целиком стартует, отвечает и корректно останавливается. Реальный адрес
   берётся через шов `App.Addr()` (порт `:0`, ОС выбирает свободный).

### 3.4. Паттерны асинхронных тестов

Асинхронное поведение нельзя проверять `time.Sleep` — это и медленно, и нестабильно. Вместо этого:

```go
require.EventuallyWithT(t, func(c *assert.CollectT) {
	assert.Len(c, probe.attempts(), 2)
}, 10*time.Second, 50*time.Millisecond)
```

«Проверяй каждые 50 мс, пока условие не станет истинным, но не дольше 10 с».

**Как проверить, что ничего не пришло?** Нельзя «подождать и убедиться, что пусто». Приём — **сентинел**:
положить в топик маркер и убедиться, что получен **только** маркер. Раз маркер дошёл, всё, что было до него,
тоже дошло бы.

### 3.5. Покрытие (`task cover`)

`task cover` гоняет unit + integration с `-coverprofile` и проверяет пороги `go-test-coverage`
(`services/<svc>/.testcoverage.yml`):

```yaml
threshold:
  total: 70          # весь модуль
override:
  - path: /domain$
    threshold: 80    # бизнес-логика строже
  - path: /service$
    threshold: 80
exclude:
  paths: [ (^|/)mocks/, ^cmd/, (^|/)docs/ ]   # сгенерированный код не считаем
```

Сейчас итог по сервисам 91–96%. Помните: покрытие показывает, что строка **выполнялась**, а не что
она **проверена**. Тест без ассертов даёт 100% и ничего не гарантирует.

## 4. E2E-тесты

### 4.1. Что это

E2E (end-to-end) — **чёрный ящик**. Тест ничего не знает о внутренностях: он шлёт HTTP-запрос в gateway,
как настоящий клиент, и проверяет наблюдаемый результат — ответ API и появление уведомления.

Путь, который проверяется одним тестом:

```
HTTP → gateway → gRPC → order → (Postgres: orders + outbox) → Debezium CDC → Kafka → notification → Postgres
                         ├→ user (пользователь, адрес)
                         └→ product (цены, имена)
```

Ни integration, ни unit не проверяют, что **Debezium** действительно забирает outbox и что сообщение
в Kafka выглядит так, как ждёт notification.

### 4.2. Как устроено

- Отдельный compose-проект `delivery-e2e` (`e2e/compose.yaml`): свои порты и имена, не мешает dev-стеку.
- `task e2e-images-check` следит, чтобы версии образов совпадали с основным `compose.yaml`.
- `TestMain` (`e2e/stack_e2e_test.go`) ждёт готовности стека и загружает seed-данные.

```bash
task e2e                  # поднять → тесты → снести (≈ 1 мин)
E2E_KEEP=1 task e2e       # оставить стек после прогона для разбора
task e2e-logs             # логи контейнеров
task e2e-down
```

### 4.3. Сценарии

| Тест | Что проверяет |
|---|---|
| `TestCreateOrder_HappyPath` | Заказ создаётся, сумма = цены × количество, уведомление пришло с правильным payload |
| `TestCreateOrder_ClientErrors` | Невалидный запрос → 4xx |
| `TestCreateOrder_NotFound` | Несуществующий товар → 404 |
| `TestCreateOrder_Trace` | Спаны **всех пяти** сервисов под одним `TraceId`; клиентский `traceparent` попадает только в `Links` (gateway — граница доверия) |
| `TestResilience_NotificationDown` | notification остановлен → заказы создаются, после старта уведомления догоняют |
| `TestResilience_DebeziumDown` | То же для CDC: outbox копится и доезжает после восстановления |
| `TestResilience_Redelivery` | Оффсет сдвинут назад → сообщения пришли повторно, но дублей уведомлений нет (inbox) |

Реальная находка e2e: тип события был `OrderCreated` вместо `order.created`, а суммы — строками.
Unit- и integration-тесты этого не видели, потому что продюсер и консьюмер «договорились» неправильно
одинаково. После этого появился единый эталон в `contracts/events/`.

## 5. Бенчмарки (micro-benchmarks)

### 5.1. Что это

Benchmark измеряет **скорость и аллокации** одной функции. Это не нагрузочный тест системы, а «микроскоп»
для горячих путей: middleware, построение события, `CreateOrder` с моками.

```go
func BenchmarkNewOrder(b *testing.B) {
	for b.Loop() {          // Go 1.24+: сам решает, сколько итераций
		_, _ = domain.NewOrder(/* ... */)
	}
}
```

### 5.2. Как читать

```
BenchmarkOrderService_CreateOrder-12    512340    2310 ns/op    1456 B/op    23 allocs/op
```

- `-12` — GOMAXPROCS;
- `512340` — сколько итераций прогнали;
- `ns/op` — время на одну операцию;
- `B/op`, `allocs/op` — байты и число аллокаций в куче на операцию. Часто важнее времени:
  аллокации нагружают GC.

### 5.3. Сравнение с эталоном

Один прогон — шум. Поэтому бенчмарк гоняется несколько раз и сравнивается статистически через `benchstat`:

```bash
task bench            # → load/bench/new.txt
task bench-compare    # benchstat baseline.txt vs new.txt
task bench-baseline   # принять new.txt как новый эталон (руками, после осознанного изменения)
```

```
              │ baseline │              new               │
              │  sec/op  │   sec/op     vs base           │
CreateOrder-12  2.31µ ±1%   2.95µ ±2%  +27.71% (p=0.000 n=10)
```

`p=0.000` — разница статистически значима. Если видите `~` вместо процента — различия нет, это шум.

## 6. Нагрузочное тестирование (k6, ghz)

### 6.1. Зачем

Функциональные тесты отвечают «работает ли». Нагрузочные — **«сколько выдержит и что сломается первым»**.
Целевых SLO в проекте нет, поэтому задача была: найти предел, узкое место и зафиксировать **baseline**.

### 6.2. Базовые термины

- **RPS** — запросов в секунду.
- **Latency** — время ответа. Смотрим не среднее, а **перцентили**:
  - **p50** (медиана) — половина запросов быстрее;
  - **p95** — 95% запросов быстрее, 5% — медленнее. Это «типичный плохой случай»;
  - **p99** — хвост. Его чувствует каждый сотый запрос, а при 10 запросах на страницу — почти каждый пользователь.

  Почему не среднее: 99 запросов по 2 мс и один по 2000 мс дают среднее ~22 мс — число, которого никто не видел.
- **Error rate** — доля ошибок.
- **Open model (arrival rate)** — k6 запускает итерации с заданной частотой независимо от того, успел ли
  сервер ответить. Так ведут себя реальные пользователи. Если k6 не хватает виртуальных пользователей (VU),
  чтобы держать темп, итерации пропускаются — это `dropped_iterations`, признак насыщения.
- **Деградация** — момент, когда p95 или ошибки резко растут при небольшом росте RPS.

### 6.3. Стек и профили

Нагрузка идёт на **изолированный** стек `delivery-load` (`load/compose.yaml`) с **лимитами CPU и памяти**
на каждый контейнер — иначе результат зависит от того, что ещё запущено на ноутбуке.

```bash
task load-up              # поднять стек (Grafana: http://localhost:38300)
task load-smoke           # 5 RPS × 1 мин — «стек вообще живой?»
task load-stress          # ступени RPS до деградации — поиск предела
task load-regression      # 70% от предела × 5 мин — гейт регрессий, ненулевой код при превышении порогов
task load-soak            # то же RPS × 30 мин — утечки и деградация со временем
task load-grpc            # ghz по каждому gRPC-методу, ступени concurrency
task load-lag             # лаг «заказ → уведомление» по ступеням
task load-down
```

| Профиль | Вопрос | Как понять результат |
|---|---|---|
| smoke | Работает ли сценарий? | 0 ошибок |
| stress | Где предел? | Последняя ступень до срабатывания критерия (p95 в N раз выше эталона) |
| regression | Не стало ли хуже после изменения? | Exit code: 0 — ок; иначе превышен p95 или ошибки |
| soak | Не течёт ли что-то со временем? | `task load-soak-leaks`: рост горутин и heap начало vs конец |

Логика k6-сценария тоже покрыта тестами: `task load-js-test` (node --test).

### 6.4. Как читать результат: `load/results/baseline.md`

Отчёт — образец того, как оформлять нагрузочное исследование. Ключевые места:

1. **Окружение** — железо, версии, лимиты контейнеров. Без этого числа бессмысленны.
2. **Таблица ступеней stress.** Смотрите на тренды:

   | Ступень | RPS | p95, мс | p99, мс | CPU order |
   |---|---|---|---|---|
   | 10 | 250 | 3.5 | 14.9 | 28% |
   | 15 | 375 | 5.2 | 25.5 | 43% |
   | 16 ⚠ | 400 → 390 | **19.7** | **120.8** | 36% |

   p95 вырос в 4 раза, при этом **CPU не упёрся** (36% от лимита в 1 ядро). Значит, узкое место не CPU,
   а ожидание чего-то.
3. **Доказательства узкого места** — трейсы медленных запросов: из 108 мс 76 мс — `pool.acquire` в `order`.
   То есть запросы стоят в очереди за соединением к Postgres (пул pgx = 10 соединений).
4. **Открытые вопросы** — честно записано, что гипотеза требует проверки.

Это главный навык: **числа нагрузки → гипотеза → подтверждение трейсами, метриками, профилем.**
Как это делать в Grafana — во второй лекции.

### 6.5. Soak-находка

30 минут на 260 RPS: утечек памяти и горутин нет, но p99 к концу вырос в 3.78 раза, доля ожиданий пула
`order` выросла с 0.01% до 1.08%, был провал ~10 с. Вердикт `failed` оставлен как находка: долгий прогон
показал то, чего не видно за 5 минут (рост таблиц `outbox_events`/`inbox_events` без ретенции — один из кандидатов).

## 7. Профилирование (pprof, Pyroscope)

Профиль отвечает на вопрос **«на что тратится ресурс»** — построчно, до функции.

| Тип | Что показывает |
|---|---|
| `profile` (CPU) | Где процессор проводит время |
| `heap` / `allocs` | Кто держит память / кто аллоцирует |
| `goroutine` | Где сейчас стоят все горутины (утечки, блокировки) |
| `mutex` / `block` | Где горутины ждут мьютексы / каналы / I/O |
| `trace` | Хронология планировщика, GC, системных вызовов |

Три способа снять:

```bash
# 1. По запросу с локального сервиса (debug-порты 6060–6064)
task pprof SERVICE=order TYPE=profile SECONDS=30
go tool pprof -http=:0 tmp/pprof/order-profile-<ts>.pb.gz

# 2. Автоматически в load-stress/soak + сравнение с эталоном
task load-pprof-diff SERVICE=order TYPE=heap

# 3. Непрерывно: Alloy → Pyroscope → Grafana (flame graph, см. лекцию 2)
```

Нюанс: CPU-профайлер в процессе один. Если запущен Alloy (`task compose-up`), он его почти всё время
держит, и `task pprof TYPE=profile` вернёт HTTP 500 — остановите `docker compose stop alloy`.

## 8. Шпаргалка: какой тест писать

| Ситуация | Тест |
|---|---|
| Новое бизнес-правило в `domain` | unit, табличный |
| Новый сценарий в `service` | unit с моками mockery; отказы каждой зависимости — отдельными кейсами |
| Новый SQL-запрос / репозиторий | integration через `pgtest.NewDB` |
| Новая миграция | уже покрыта `CheckMigrations` — проверьте, что `down` полный |
| Меняется формат события Kafka | обновить `contracts/events/*.json`, golden-тесты в продюсере и консьюмере |
| Парсинг внешнего ввода | unit + fuzz-цель |
| Новый сквозной сценарий пользователя | e2e (одного-двух достаточно, детали — ниже по пирамиде) |
| Оптимизация горячего пути | benchmark до/после + `benchstat` |
| Изменение, влияющее на производительность | `task load-regression` до и после |
| Баг | сначала тест, который его воспроизводит (красный), потом фикс (зелёный) |

## 9. Практика

1. `task test` — посмотрите вывод, затем удалите одну строку `EXPECT()` в `order/internal/service/order_test.go`
   и запустите снова. Прочитайте сообщение строгого мока. Верните строку.
2. В `services/order/internal/service/order.go` поменяйте порядок: сохранение заказа **до** проверки товаров.
   Какой кейс упадёт и почему?
3. `task -d services/order test-integration` — найдите в выводе (`-v`) создание контейнера Postgres.
4. Сломайте `down`-миграцию в `order` (закомментируйте `DROP TABLE`) — какой тест поймает?
5. `E2E_KEEP=1 task e2e`, затем прочитайте `e2e/trace_e2e_test.go` и повторите его SQL руками
   в ClickHouse e2e-стека (Grafana в нём нет, только ClickHouse на `127.0.0.1:28123`):
   `docker compose -p delivery-e2e exec clickhouse clickhouse-client -q "SELECT ServiceName, count() FROM otel.otel_traces GROUP BY ServiceName"`.
6. `task bench`, затем добавьте лишнюю аллокацию в `domain.NewOrder` и выполните `task bench-compare`.
7. `task load-up && task load-smoke`, откройте дашборд «Delivery / Load» (http://localhost:38300) и
   сопоставьте числа k6 и метрики сервисов (подробно — во второй лекции).
