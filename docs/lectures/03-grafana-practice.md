# Практикум 3. Grafana руками: маршрут и сценарии аварий

> Лекции [1](01-testing.md) и [2](02-observability-grafana.md) — теория и справочник.
> Этот практикум — тренажёр: вы сами ломаете систему и учитесь находить поломку по Grafana.
> Чувство «захожу и теряюсь» проходит не от чтения, а после 5–10 таких расследований.

---

## 0. Почему теряешься и что с этим делать

В Grafana пять дашбордов и около сотни панелей. Если открыть их без вопроса, глазу не за что зацепиться.
Решение — **всегда приходить с вопросом и идти по одному маршруту**.

### Три вопроса — три шага

| Шаг | Вопрос | Куда смотреть | Что игнорировать на этом шаге |
|---|---|---|---|
| 1 | **Есть ли проблема?** | Services Overview → таблица «Сводка» | Всё, что ниже таблицы |
| 2 | **Где она?** | Services Overview → графики по времени, затем Service Dashboard подозрительного сервиса | Internal-спаны, runtime |
| 3 | **Почему?** | Traces Explorer → один медленный или ошибочный трейс → его логи; при необходимости Postgres/Runtime/Pyroscope | Всё остальное |

Не нужно понимать все панели. Для 90% ситуаций хватает **таблицы «Сводка», графиков p95/ошибок и
одного трейса**. Остальные панели — для проверки гипотезы, когда она уже есть.

### Маршрут «5 минут» — делайте его каждый раз одинаково

1. Открыть **Delivery / Services Overview**. Справа вверху: `Last 15 minutes`, refresh `10s`.
2. **Таблица «Сводка»**: у какого сервиса `error_rate` > 0 или p95 выше обычного? Запомните его.
3. Пролистать до **графиков** gateway и gRPC: **когда** началось? Растёт или ступенька?
4. Кликнуть по сервису в таблице → **Service Dashboard** → таблица **Slowest Server Operations** / **Top Errors**.
5. **Traces Explorer**: `service = <ваш>`, `status = Error` или `min_duration = 100ms` → открыть 1–2 трейса.
6. В трейсе найти **самый длинный или красный спан**. Это ответ на вопрос «где».
7. Из спана → **логи** этого трейса. Это ответ на вопрос «почему».
8. Вслух (или в заметке) сформулировать: «Симптом X, место Y, причина Z, подтверждено сигналами A и B».

Распечатайте этот список или держите его рядом, пока маршрут не станет автоматическим.

## 1. Подготовка

```bash
task compose-up                                      # инфраструктура + наблюдаемость
# в services/*/.env:  OTEL_ENABLED=true             (в .env.example стоит false!)
task migrate-up
task connect-register                                # коннектор Debezium (если ещё не регистрировали)
task watch-all                                       # сервисы; оставьте этот терминал открытым
```

Во втором терминале — генератор трафика:

```bash
docs/lectures/traffic.sh                             # ~5 RPS успешных заказов, Ctrl+C — стоп
```

Значки в выводе: `.` — успех (2xx), `c` — ошибка клиента (4xx), `E` — ошибка сервера (5xx), `T` — таймаут.

Режимы:

| Команда | Что шлёт |
|---|---|
| `docs/lectures/traffic.sh` | успешные заказы |
| `MODE=notfound docs/lectures/traffic.sh` | заказ с несуществующим товаром (404) |
| `MODE=invalid docs/lectures/traffic.sh` | невалидный запрос, quantity = 0 (400) |
| `PARALLEL=30 PAUSE=0 docs/lectures/traffic.sh` | 30 потоков без пауз — для сценариев с нагрузкой |

Grafana: http://localhost:3001 → Dashboards → папка **Delivery**.

> Во всех сценариях сначала попробуйте ответить на вопросы сами, и только потом раскрывайте блок
> «Что должно быть видно». Числа в ответах сняты на реальном прогоне 2026-11-03 (MacBook, dev-окружение);
> на вашей машине они будут другими, но картина — та же.

## Сценарий 0. Знакомство с нормой

**Без этого шага остальные не работают:** аномалию видно только на фоне нормы.

Запустите `traffic.sh` на 5 минут и заполните таблицу своими числами:

| Что | Где | Ваше значение |
|---|---|---|
| RPS gateway | Сводка → `rps` | |
| RPS order / user / product | Сводка | |
| p95 gateway | Сводка → `p95` | |
| p95 order `CreateOrder` | gRPC p95 по методам | |
| Утилизация пула order | Postgres → Утилизация пула | |
| Goroutines order | Runtime → Goroutines | |
| Kafka fetch records /s | Kafka | |
| Длительность одного трейса gateway | Traces Explorer → любой трейс | |
| Время от ответа gateway до спана notification | тот же трейс | |

Вопросы:
1. Почему RPS user примерно вдвое больше RPS order?
2. Почему Kafka fetch records /s ≈ RPS gateway?
3. Из каких спанов складывается время одного трейса? Какой самый длинный?

<details><summary>Что должно быть видно</summary>

Значения, снятые на реальном прогоне `traffic.sh` (MacBook, dev-окружение, 3 минуты):

| Что | Панель | Точно, по трейсам (SQL из раздела 8 лекции 2) |
|---|---|---|
| RPS gateway / order / product | 4.2 | — |
| RPS user | 8.3 | — |
| p95 gateway | 23.7 мс | **16.4 мс** (p50 10.9) |
| p95 order `CreateOrder` | 23.5 мс | **14.9 мс** |
| p95 product / user | 4.75 мс у всех трёх методов | **2.2 / 2.9 / 1.5 мс** |
| Утилизация пулов | 0 | — |
| Goroutines | 55–68, ровная линия | — |
| Kafka fetch records /s | 4.2 | — |
| Асинхронный лаг до notification | — | p50 0.52 с, p95 0.87 с |

1. На каждый заказ order вызывает в user-сервисе два метода: `GetUser` и `GetAddress`
   (`address.v1.AddressService` обслуживает тот же сервис user), и один раз product (`GetProducts`).
2. Каждый заказ порождает одно событие `order.created` → одно сообщение в Kafka.
3. Реальный трейс одного заказа (время от начала, мс):

   ```
   0.0   gateway       Server    POST /api/v1/orders                      10.7
   0.2   gateway       Client    order.v1.OrderService/CreateOrder        10.2
   0.7   order         Server    order.v1.OrderService/CreateOrder         9.5
   0.8   order         Client    user.v1.UserService/GetUser               2.5
   1.4   user          Client      SELECT                                  1.5
   3.4   order         Client    address.v1.AddressService/GetAddress      1.1
   4.6   order         Client    product.v1.ProductService/GetProducts     1.7
   6.3   order         Client    pool.acquire                              0.01
   6.4   order         Client    BEGIN → INSERT → copy_from "order_items" → INSERT → COMMIT   ~3.6
   897.5 notification  Consumer  order.events.v1 receive / process         2.4
   897.7 notification  Client      BEGIN → INSERT → … → COMMIT
   ```

   Самая заметная часть — три gRPC-вызова и транзакция в order. Асинхронная часть начинается через ~0.9 с:
   это задержка CDC (Debezium).

**Две находки, которые видны уже на норме:**

- **p95 на панели заметно больше точного** (23.7 против 16.4 мс), а у трёх разных методов он одинаковый —
  4.75 мс. Это не ошибка, а грубые бакеты гистограммы: всё, что попало в бакет 1–5 мс, интерполируется
  примерно в одно число. **Панели — для трендов и сравнения «до/после», точные числа — из трейсов.**
- **`GetUser`, `GetAddress` и `GetProducts` шли последовательно**, хотя не зависят друг от друга.
  Трейс прямо подсказал оптимизацию, и её сделали: теперь `OrderService.resolve` запускает их параллельно
  через `errgroup`. В новом трейсе три спана начинаются в одну и ту же миллисекунду, трейс — 5.5 мс
  вместо 10.7, p50 gateway — 8.7 мс вместо 10.9. Если у вас вызовы идут ступенькой — у вас старая версия.
</details>

## Сценарий 1. Ошибки клиента — это не авария

```bash
MODE=notfound docs/lectures/traffic.sh               # 1–2 минуты, параллельно с обычным traffic.sh
```

Вопросы:
1. Какая колонка Сводки изменилась: `error_rate` или `client_error_rate`? У каких сервисов?
2. С каким gRPC-кодом отвечает product или order? Где это видно?
3. Найдите в **Logs Explorer** лог такого запроса и перейдите из него в трейс.

<details><summary>Что должно быть видно</summary>

Реальная Сводка за минуту (половина запросов — `notfound`):

```
service | rps   | error_rate | client_error_rate | p95
gateway | 8.4   | 0          | 0.494             | 20 мс
order   | 8.0   | 0          | 0.471             | 18 мс
product | 8.1   | 0          | 0                 | 4.75 мс
user    | 16.1  | 0          | 0                 | 4.75 мс
```

1. `client_error_rate` ≈ 0.5 у gateway (HTTP 404) и у order (`NOT_FOUND`). `error_rate` = 0: сервис
   отработал правильно, плохие данные прислал клиент. user и product вызываются как обычно: то, что товара
   нет, order узнаёт только из ответа product.
2. `NOT_FOUND`. Видно в атрибутах лога (`grpc.code: NotFound`, `error.code: NOT_FOUND`) и в статусе спана.
3. Logs Explorer → `level_filter = WARN` (такие ошибки пишутся уровнем **WARN**, а не ERROR) → сообщения
   `grpc request failed` (order) и `http request failed` (gateway). Текст общий, подробности — в атрибутах:

   ```
   order:   error.cause = order: product not found   error.code = NOT_FOUND   grpc.code = NotFound
   gateway: error.cause = rpc error: code = NotFound desc = not found   http.status_code = 404   request_id = …
   ```

   Раскройте строку → `TraceId` → трейс. Поиск по `search = not found` по телу лога ничего не найдёт —
   эта строка лежит в атрибутах. Там же `grpc.duration_ms` / `http.duration_ms` — длительность в
   миллисекундах (`4.35`). До исправления там были наносекунды (`2770458`), см. «Что нашёл этот практикум».

**Ловушка:** у **клиентского** спана `CreateOrder` в gateway статус `Error` («not found»), хотя серверный
спан в order — без ошибки. Так ведёт себя `otelgrpc`: на клиенте ошибкой считается любой код, кроме `OK`.
Поэтому в **Service Dashboard** для gateway панель «Error Rate (Client)» покажет ~50% ошибок, а Сводка — 0.
Это не противоречие: две панели считают разное.

**Вывод:** 4xx — повод проверить клиента или API-контракт, но не повод будить дежурного. Поэтому на
дашборде две разные колонки.
</details>

## Сценарий 2. Упал сервис-зависимость

При работающем `traffic.sh` остановите **product**. `task watch-all` останавливать не нужно — достаточно
завершить процесс самого сервиса, Air останется жить:

```bash
pkill -f services/product/tmp/main          # product лежит
# через 1–2 минуты: сохраните любой .go-файл product (Cmd+S в редакторе) — Air пересоберёт и запустит его
```

(`touch` не сработает: Air реагирует на запись в файл, а не на смену времени изменения.)

Вопросы:
1. Какие значки пишет `traffic.sh`?
2. У какого сервиса вырос `error_rate`? Почему у product его нет?
3. Как выглядит Service Map в Traces Explorer?
4. Какой спан в трейсе красный и что написано в его статусе?

<details><summary>Что должно быть видно</summary>

Реальная Сводка через минуту после остановки:

```
service | rps  | error_rate | client_error_rate | p95
gateway | 4.3  | 0.97       | 0                 | 9.5 мс
order   | 4.3  | 1.0        | 0                 | 8.9 мс
user    | 8.6  | 0          | 0                 | 4.75 мс
```

1. Сплошные `E`: gateway отвечает **503**.
2. `error_rate` ≈ 1 у gateway и order. **Строки product в Сводке нет вообще**: мёртвый сервис ничего не
   пишет. Отсутствие данных — тоже сигнал: если сервис пропал из Сводки, он не работает.
   Обратите внимание: user по-прежнему получает запросы — order успевает спросить пользователя и адрес,
   прежде чем упасть на product.
3. Ребро order → product красное.
4. Цепочка ошибок в трейсе — читайте её **снизу вверх**, первопричина в самом глубоком спане:

   ```
   gateway  Server  POST /api/v1/orders                    Error (HTTP 503)
   gateway  Client  order.v1.OrderService/CreateOrder      Error: unavailable
   order    Server  order.v1.OrderService/CreateOrder      Error: unavailable
   order    Client  product.v1.ProductService/GetProducts  Error: dial tcp 127.0.0.1:8092: connect: connection refused
   ```

   В логах order — уровень **ERROR** (в отличие от 404 в сценарии 1, там был WARN) с тем же `TraceId`
   и `error.cause = … connection refused`. В логах gateway — `http.status_code = 503`.

**Неожиданное:** p95 **упал** с 24 до 9.5 мс. Ошибка возвращается быстрее успешного заказа: нет записи в БД.
Падение задержки на фоне роста ошибок — тоже симптом аварии, а не улучшение.

**Восстановление не мгновенное.** Процесс product поднялся через 2 с, а успешные заказы пошли через ~37 с.
Скорее всего, это экспоненциальная задержка переподключения (backoff) gRPC-клиента в order: пока product
лежал, интервал между попытками соединиться вырос. Значит, после короткого падения зависимости сервис
ещё какое-то время отдаёт ошибки.
</details>

## Сценарий 3. Медленная зависимость

Временно добавьте задержку в `services/product/internal/service/product.go`, в начало `GetProducts`:

```go
time.Sleep(200 * time.Millisecond) // TODO: убрать после практикума
```

Air перезапустит product сам. Трафик — обычный `traffic.sh`.

Вопросы:
1. У каких сервисов вырос p95 в Сводке? У каких нет?
2. Как по графикам отличить «тормозит product» от «тормозит order»?
3. Что показывает heatmap **Duration Distribution** в Traces Explorer?
4. Почему `error_rate` остался нулевым и чем это опасно?

<details><summary>Что должно быть видно</summary>

Реальная Сводка через минуту:

```
service | rps  | error_rate | p95
gateway | 2.25 | 0          | 245 мс
order   | 2.25 | 0          | 245 мс
product | 2.27 | 0          | 243 мс
user    | 4.53 | 0          | 4.75 мс
```

И точный p95 по спанам — от самого внешнего к самому глубокому:

```
gateway  Server  POST /api/v1/orders                    219.7 мс
gateway  Client  order.v1.OrderService/CreateOrder      219.1
order    Server  order.v1.OrderService/CreateOrder      218.2
order    Client  product.v1.ProductService/GetProducts  205.0
product  Server  product.v1.ProductService/GetProducts  204.1   ← здесь время и рождается
order    Client  user.v1.UserService/GetUser              3.5   ← а здесь всё как было
```

1. p95 вырос у product, order и gateway (они ждут product). У user — нет.
2. p95 **сервера** product (204 мс) почти равен p95 **клиентского** вызова из order (205 мс). Значит,
   время уходит внутри product. Если бы клиентский спан был сильно длиннее серверного — время терялось бы
   между ними: сеть, очередь, переподключение.
3. Полоса точек «прыгнула» вверх в момент изменения — видно, **когда** началось.
4. Ошибок нет, всё «работает», просто медленно. Без перцентилей и трейсов такую деградацию не заметить.

**Неожиданное: RPS упал вдвое** (4.2 → 2.25), и Kafka fetch records /s — тоже. Никто не стал присылать
меньше заказов: `traffic.sh` ждёт ответа перед следующим запросом (*закрытая модель нагрузки*), поэтому
медленный сервер сам снижает поток запросов. Настоящие пользователи так не делают, их запросы копятся. Поэтому k6
в load-стеке работает по *открытой модели* (`arrival rate`) и честно показывает `dropped_iterations`.
Вывод для чтения дашбордов: **падение RPS вместе с ростом задержки — часто следствие, а не причина**.

**Не забудьте удалить `time.Sleep`.**
</details>

## Сценарий 4. Тихая поломка: notification не работает

Остановите notification (его процесс Air), трафик — обычный. Подождите 2–3 минуты, затем запустите снова.

Вопросы:
1. Что показывает `traffic.sh`? Что показывает Сводка?
2. По какой панели всё-таки видно поломку?
3. Что происходит после запуска notification?

<details><summary>Что должно быть видно</summary>

1. Сплошные `.`, Сводка зелёная, все числа как в норме. Это **тихая поломка** — самая опасная:
   клиент ничего не замечает, а уведомления не уходят.
2. Признаки — только косвенные, и их надо уметь заметить:
   - график **Kafka: fetch records /s** не падает в ноль, а **обрывается**: эту метрику пишет сам consumer,
     а он мёртв. Пустой хвост графика — это не «0 событий», это «некому сообщить»;
   - на **Goroutines** и других графиках Runtime стало 4 линии вместо 5;
   - в Сводке notification не было и раньше: у него нет HTTP/gRPC-сервера, только consumer;
   - в новых трейсах нет асинхронной части.

   Сколько накопилось, Grafana не показывает. Это видно в Redpanda Console (http://localhost:3000 →
   Consumer Groups → `notification`) или командой:

   ```bash
   docker exec redpanda rpk group describe notification   # STATE Empty, MEMBERS 0, TOTAL-LAG 435
   ```
3. Реально: процесс поднялся через 2 с, отставание 435 сообщений разобрано меньше чем за 2 с, на графике —
   одна точка **52 записи/с** вместо обычных 4.2, затем снова норма. Ни одно уведомление не потерялось
   (Kafka хранит сообщения, inbox не даёт дублей). У этих заказов в трейсе асинхронная часть отстоит
   не на 0.9 с, а на минуты — лаг доставки виден прямо в waterfall.

**Вывод:** именно для таких поломок нужны алерты на бизнес-показатели («уведомлений нет 5 минут»).
В проекте их пока нет — это пробел, найденный самостоятельно.
</details>

## Сценарий 5. Тихая поломка глубже: остановлен Debezium

```bash
docker stop debezium        # через 2–3 минуты: docker start debezium
```

Вопросы:
1. Чем картина отличается от сценария 4? notification при этом жив?
2. Как убедиться, что заказы копятся, а не теряются?
3. Что происходит после `docker start debezium`?

<details><summary>Что должно быть видно</summary>

1. Сводка снова зелёная, `traffic.sh` пишет `.`. notification **жив**: на Goroutines 5 линий, у группы
   consumer'ов есть участник, `TOTAL-LAG 0`. Но график **Kafka: fetch records /s обрывается точно так же,
   как в сценарии 4**. Счётчик с delta-temporality не выгружается, если за 10 с не было ни одного события,
   поэтому «consumer мёртв» и «читать нечего» на этой панели выглядят одинаково. Различают их по Runtime
   (есть ли notification) и по consumer group.

   Debezium не инструментирован OpenTelemetry, поэтому **в Grafana его нет вообще**. Поломку видно только
   по следствию.
2. Смотреть надо на Kafka, а не на outbox. Таблица `outbox_events` **не чистится** (в dev-базе после
   нагрузочных прогонов ~166 тыс. строк), поэтому её рост — норма в любом случае. Признак поломки —
   замерший конечный оффсет топика:

   ```bash
   docker exec redpanda rpk group describe notification
   # LOG-END-OFFSET 165971 и не меняется, LAG 0 — consumer всё прочитал, новых сообщений нет
   ```

   И время последнего уведомления:
   `docker exec notification-postgres psql -U postgres -d notificationdb -tAc "SELECT now() - max(created_at) FROM notifications"`
   — реально было 1 мин 34 с при обычных долях секунды.
3. Реально: коннектор перешёл в `RUNNING` через ~13 с после `docker start`, оффсет сразу вырос на ~500
   (накопленное за остановку), последнее уведомление — 0.03 с назад. Debezium дочитал WAL с места
   остановки, ничего не потерялось. Если не пошло — `curl -s localhost:8083/connectors/order-outbox/status`
   (при необходимости `task connect-register`).

**Вывод:** observability покрывает ровно то, что инструментировано. Компонент без телеметрии —
«слепое пятно», которое видно только по косвенным признакам.
</details>

## Сценарий 6. Узкое место — пул соединений к БД

Это сценарий про **проверку гипотезы**: нагрузочный тест заподозрил, что order упирается в пул из 10
соединений. Проверим экспериментом.

1. Нагрузка `PARALLEL=30 PAUSE=0 docs/lectures/traffic.sh` на 1 минуту с обычным `PG_MAX_CONNS=10`.
2. То же с `PG_MAX_CONNS=2`, затем с `PG_MAX_CONNS=30` в `services/order/.env`. Air не следит за `.env`:
   после правки сохраните любой `.go`-файл order, чтобы он перезапустился.

Вопросы:
1. Что показывает группа **Postgres (pgxpool)** при пуле 10?
2. Насколько хуже при 2 и насколько лучше при 30?
3. Подтвердилась ли гипотеза? Если нет — где на самом деле узкое место?

<details><summary>Что было на реальном прогоне</summary>

| `PG_MAX_CONNS` | RPS gateway | Утилизация пула order | Empty acquire /s | p95 `pool.acquire` | p95 `COMMIT` | p95 `CreateOrder` |
|---|---|---|---|---|---|---|
| 10 | 427 | скачет 0–1 | ~200 | 10.8 мс | 11.8 мс | 49.7 мс |
| 2 | 412 | полка на 1.0 | ~245 | 14.4 мс | 14.1 мс | 53.0 мс |
| 30 | 474 | полка на 1.0 (30 из 30!) | ~235 | 14.5 мс | 14.3 мс | 55.4 мс |

1. Уже при пуле 10 — сотни ожиданий соединения в секунду и длинный `pool.acquire` в трейсах. Похоже на
   нехватку пула — та же картина, что в `load/results/baseline.md`.
2. Почти никакой разницы ни в одну сторону. Пул из 30 соединений тоже занят полностью.
3. **Гипотеза не подтвердилась.** Если бы дело было в количестве соединений, 30 помогли бы. Подсказка
   в трейсах: `BEGIN`, который должен занимать доли миллисекунды, имеет p95 **8 мс**. Тормозит не очередь
   к пулу, а сама работа с базой: каждое соединение держится дольше, чем нужно.

   Дальше — `uptime` и `docker stats`: **load average 30 при 12 ядрах**, order-postgres ~50% CPU,
   ClickHouse ~45%, Debezium ~26%. Машина перегружена целиком, и заметную долю съедает сам генератор:
   30 процессов `curl` стартуют сотни раз в секунду (вместе с ними — системные `cfprefsd`, `opendirectoryd`).

**Вывод:** на ноутбуке, где генератор нагрузки, сервисы и вся инфраструктура делят одни ядра, предел
сервиса **не измерить**. Поэтому в проекте есть отдельный стек `delivery-load` с лимитами CPU на каждый
контейнер и k6 (лекция 1, раздел 6). Метрики пула честно показали ожидание, но причину ожидания дал
только второй и третий сигнал (трейс `BEGIN` и CPU машины). Не останавливайтесь на первом правдоподобном объяснении.

**Верните `PG_MAX_CONNS=10`.**
</details>

Временно добавьте в начало `GetProducts` (product) бесполезную работу (и импорт `crypto/sha256`):

1. Explore → Pyroscope → `service_name = product`, тип `process_cpu`. Какая функция самая широкая сверху?
2. Сравните период до и после изменения (Comparison/Diff). Что стало красным?
3. Видно ли то же самое в трейсе? Чем трейс и профиль отличаются?

<details><summary>Что должно быть видно</summary>

Реальный профиль CPU product за 2 минуты (доля от всего CPU процесса):

```
total (функция + всё, что она вызывает)        self (только сама функция)
 62%  grpc ... _ProductService_GetProducts_Handler   21.8%  runtime.pthread_cond_signal
 59%  service.(*ProductService).GetProducts          18.1%  crypto/internal/fips140/sha256.blockSHA2
 48%  crypto/sha256.Sum256                           11.9%  syscall.rawsyscalln
  9.5% pgxpool.(*Pool).Query                          9.3%  sha256.(*Digest).checkSum
```

1. Самый широкий блок наверху (по self) — **не наш код**, а `runtime.pthread_cond_signal`: служебная
   работа планировщика Go, когда горутины будят друг друга. Это частая ловушка. Правильный способ — идти по

2. Красное — sha256 и цепочка над ним.
3. **В трейсах почти незаметно**: p95 серверного спана product 3.4 мс против 2.2 мс в норме. Пока CPU не
   насыщен, лишняя работа почти не увеличивает задержку — она «бесплатна», пока не кончатся ядра. Профиль
   показывает её сразу. Трейс отвечает «где в системе», профиль — «где в коде и на что уходит ресурс».

**Удалите добавленный код.**

## Сценарий 8. Расследование вслепую

Когда сценарии 0–7 пройдены, тренируйтесь без подсказок. Скрипт ломает случайный компонент и не говорит какой:

```bash
docs/lectures/traffic.sh               # трафик во втором терминале
docs/lectures/drill.sh start           # что-то сломалось
# ... расследование только через Grafana, по маршруту «5 минут» ...
docs/lectures/drill.sh answer          # проверить себя
docs/lectures/drill.sh stop            # починить
```

Возможные поломки: «зависшая» БД product, user или notification (`docker pause`), остановленный Debezium,
«зависшая» Kafka. Засекайте время. Цель — **меньше 5 минут** и формулировка
«симптом → место → причина → чем подтверждено».

<details><summary>Подсказка (раскройте, если застряли)</summary>

«Зависшая» БД (`docker pause`) ведёт себя совсем не так, как остановленный сервис: соединение не рвётся,
запросы **висят**. Вот что было на реальном прогоне с `docker pause product-postgres` на 45 с:

- `traffic.sh`: всего **8 значков `T`** за 45 с. Каждый запрос висел ровно 5 с — столько ждёт
  `curl --max-time 5`, — а следующий ушёл только после него (закрытая модель, см. сценарий 3);
- в трейсах — спаны **по 5 с** по всей цепочке со статусом `context canceled`, а в product — спан `connect`
  на **39.8 с**: пул pgx пытался открыть новое соединение к замороженной базе;
- в логах — только **WARN** `context canceled` в gateway, order и product;
- **`error_rate` в Сводке не растёт.** Код `Canceled` не считается серверной ошибкой. Видно только
  падение RPS почти до нуля и рост p95.

Это два реальных пробела, которые нашёл этот тренажёр:

1. **Нет серверных таймаутов.** Запрос отменил клиент (curl через 5 с). Ни gateway, ни order, ни product
   сами по таймауту не завершаются: без терпеливого клиента запрос висел бы, пока БД не «оттает».
2. **Зависание выглядит как ошибки клиента.** Алерт только на `error_rate` такую аварию пропустит.
   Нужен алерт на задержку или на падение RPS.

Не пугайтесь спанов `order.events.v1 receive` в notification длиной в секунды: это ожидание новых
сообщений (long poll), а не медленная обработка. Обработку показывает спан `process`.
</details>

## Шпаргалка «симптом → куда смотреть»

| Симптом | Первым делом | Чем подтвердить |
|---|---|---|
| Много `E` (5xx) | Сводка → у кого `error_rate` | Traces Explorer `status=Error` → самый глубокий красный спан → логи (ERROR) |
| Много `c` (4xx) | `client_error_rate` | Logs Explorer, `level_filter = WARN`, причина — в атрибуте `error.cause` |
| Всё медленно | Сводка p95 → у кого вырос **серверный** p95 | Самый длинный спан в медленном трейсе |
| RPS упал, p95 вырос, `error_rate` = 0 | Зависшая зависимость (БД, Kafka) | Спаны по 5 с с `context canceled`, долгий `connect` |
| p95 **упал**, ошибки выросли | Отказ: ошибки отвечают быстрее успеха | `error_rate`, красные спаны |
| Сервис пропал из Сводки / линия Runtime исчезла | Он не работает или не шлёт телеметрию | Логи в терминале `watch-all` |
| График обрывается, а не падает в 0 | Некому писать метрику или нечего считать | Есть ли сервис на Goroutines; `rpk group describe` |
| Всё зелёное, но «что-то не так» | Kafka fetch records /s, асинхронная часть трейсов | `rpk group describe notification` (оффсет, лаг), время последнего уведомления |
| Ожидание пула растёт | Postgres (pgxpool) | Трейс: длинный только `pool.acquire` (мало соединений) или и `BEGIN`/`COMMIT` (медленна сама БД / машина) |
| CPU растёт | Pyroscope flame graph — снизу вверх от своей функции | Diff с периодом до изменения |
| Горутины / память растут и не падают | Runtime | `task pprof SERVICE=<svc> TYPE=goroutine` / `heap` |
| Сервис поднялся, а ошибки ещё идут | Backoff переподключения gRPC-клиента | Подождать ~30 с, смотреть клиентские спаны |

## Что нашёл этот практикум в самом проекте

Прогон сценариев на реальном стеке выявил вещи, которых не было ни в одной спеке. Это и есть
польза observability: она показывает систему такой, какая она есть.

| Находка | Где видно | Сценарий |
|---|---|---|
| Нет серверных таймаутов: при зависшей БД запрос висит, пока его не отменит клиент | Спаны по 5 с = `curl --max-time 5` | 8 |
| Зависание зависимости не попадает в `error_rate` (`Canceled` — «клиентская» ошибка) | Сводка | 8 |
| ✅ исправлено: `GetUser`, `GetAddress`, `GetProducts` в order вызывались последовательно, хотя независимы. Теперь параллельно (`errgroup`), трейс 10.7 → 5.5 мс | Waterfall трейса | 0 |
| ✅ исправлено: атрибуты логов `grpc.duration_ms` / `http.duration_ms` содержали **наносекунды** (`592334` для 0.6 мс) — `slog.Duration` под именем с суффиксом `_ms`. Теперь `logger.Duration` пишет дробные миллисекунды | `LogAttributes` в ClickHouse | 1 |
| `outbox_events` не чистится (~166 тыс. строк в dev-базе) | `SELECT count(*)` | 5 |
| Debezium и лаг consumer'а не видны в Grafana вообще | Только `rpk` и Redpanda Console | 4, 5 |
| После падения зависимости ошибки идут ещё ~35 с из-за backoff gRPC-клиента | `traffic.sh`, клиентские спаны | 2 |
| p95 на панелях завышен в 1.5–2 раза против точного из-за крупных бакетов | Сводка против SQL по трейсам | 0 |

## А как тренироваться с тестами

Принцип тот же — ломать и смотреть, кто поймает. Упражнения есть в конце [лекции 1](01-testing.md#9-практика).
Короткий тренажёр:

| Поломка в коде | Кто должен поймать | Команда |
|---|---|---|
| Сохранять заказ, даже если товар не найден | unit-тест `service` | `task -d services/order test` |
| Опечатка в SQL репозитория | integration | `task -d services/order test-integration` |
| Удалить `DROP TABLE` из `down`-миграции | integration (`CheckMigrations`) | то же |
| Переименовать поле в событии `order.created` | golden-тест контракта | то же |
| Не записывать `traceparent` в outbox | integration + e2e `TestCreateOrder_Trace` | `task e2e` |
| Забыть закрыть горутину consumer'а | goleak | `task -d platform test` |
| Лишние аллокации в горячем пути | benchmark | `task bench && task bench-compare` |

Если поломку не поймал **ни один** тест — вы нашли дыру в покрытии. Это и есть ответ на вопрос
«достаточно ли тестов».
